# Security review and remediation

Codex Security completed one static, repository-wide scan of the initial source on 2026-09-26. It reviewed all 46 source-scope files and reported 7 findings: 3 high, 2 medium, 2 low. The scan was performed before the fixes below; it is not a certification of a public deployment.

| Initial finding | Change in current source | Verification |
| --- | --- | --- |
| Unauthenticated first-run owner claim | `SETUP_TOKEN` is generated by `pnpm setup`, kept in `.env`, required by the setup API and entered in the UI. It remains required after account deletion. | API rejects absent/wrong token; UI smoke enters the generated test token. |
| Concurrent setup creates multiple owners | Setup rechecks ownership inside `BEGIN IMMEDIATE`; SQLite has a unique singleton-owner index. | An HTTP request held mid-body cannot create a second owner after another setup succeeds. |
| Duplicate domain aliases can misroute mail | SQLite globally reserves each `kind='domain'` alias address. Migration stops with an error if older data already contains duplicates. | Singleton and alias constraints are checked by API tests and database rules. |
| Shared login limit behind reverse proxy | Only peers listed in `TRUSTED_PROXY_IPS` may supply a client IP through the final `X-Forwarded-For` entry. | API test exhausts one forwarded client bucket and confirms another client can log in. |
| Oversized provider messages consume resources | Provider JSON is capped at 8 MB, HTML input at 500,000 characters, stored body at 200,000 characters, Gmail MIME traversal at 100 parts/16 levels, and OAuth sync at 5 pages per run. Provider redirects are rejected. | Mocked provider tests cover the response cap and stored text cap. |
| Owner email timing difference | Failed login performs a comparable scrypt check with a dummy hash when no user exists. | Both branches now call the same password-verification function; API login tests pass. |
| Sensitive SQLite paths inherit broad permissions | On POSIX the app sets a restrictive umask and rejects data/database paths with group or other access; backup requires owner-only paths. | Code review and backup exercise; Windows ACLs still require operator review. |

## Remaining deployment checks

- Set the real HTTPS origin and configure OAuth client registrations and consent. Gmail's restricted read scope may require Google verification and assessment.
- If the app runs behind a reverse proxy, configure `TRUSTED_PROXY_IPS` only for that proxy and ensure it appends or overwrites `X-Forwarded-For` with the actual client address. A missing or incorrect proxy setting can still cause shared rate limits.
- Confirm effective ACLs for `.env`, SQLite, SQLite sidecars and backups on the production host. POSIX mode checks do not establish Windows ACL safety.
- Oversized provider responses fail the sync rather than silently dropping mail. The owner must inspect the mailbox error and handle such messages at the provider; real provider behavior has not been tested.
- Real Gmail, Microsoft, IMAP, DNS/MX, Cloudflare Worker routing, provider revocation and backup restore remain unverified without external accounts and infrastructure.

The patched source passed the API suite, Chrome UI smoke and package audit locally. A second full Codex Security scan has not yet been run against the patched source.
